# Architecture Decision Records (ADR / 意思決定記録)

> ユーザーとの合意によって確定した設計上の意思決定を記録します。後続のAIエージェントはこの決定を覆さず、これに従って実装を進めてください。

---

## ADR-001: 物語プロットに特化したマルチソケット型ノード構造（B案）の採用
* **Status:** Accepted (2026-11-15)
* **Context:**
  ノード間の接続方式として、単一の「前→次」のみを繋ぐシンプル型（A案）と、1つのノードに「時系列フロー」「登場人物」「伏線の提示・回収」「アイテム・条件」など複数の名前付き・型付きソケット（端子）を持たせる本格ノード型（B案）が存在した。
* **Decision:**
  **B案（名前付き・型付きマルチソケット方式）** を採用し、主用途を**物語（小説・シナリオ）のプロット構築**に特化する。
* **Consequences:**
  * 単なるフローチャートに留まらず、「どのシーンに誰が登場するか」「どこで張った伏線をどのシーンで回収するか（未回収の伏線はどれか）」をグラフ構造として厳密に追跡・可視化できる。
  * ソケットごとにデータ型（`Flow`, `Character`, `Foreshadow`, `Item`）を定義し、互換性のないソケット同士の誤接続を防ぐバリデーションを `src/core/graphEngine.ts` に実装する。

## ADR-002: `CustomTextEditorProvider` と `.nplot` (UTF-8 JSON) による永続化
* **Status:** Accepted (2026-11-15)
* **Context:**
  `genkou_sheet` と同様の操作感・信頼性を持ち、Git管理や標準のUndo/Redoと統合されたVS Code拡張機能として実装する必要がある。
* **Decision:**
  `CustomTextEditorProvider` を採用し、ファイル形式は可読性の高い整形済み JSON（拡張子 `.nplot`）として `vscode.TextDocument` と双方向同期する。
* **Consequences:**
  * VS Code 標準の保存、Undo/Redo、ファイル履歴、Git差分比較がそのまま機能する。
  * 万一拡張機能をアンインストールしても、プロットデータは人間が読める JSON テキストとして完全に保全される。

## ADR-003: 付箋（Note）から構造化ノード（Scene / Foreshadow 等）への段階的昇格UX
* **Status:** Accepted (2026-11-15)
* **Context:**
  最初からすべての入出力ソケットやパラメータを入力させるUIでは、初期のブレインストーミング（「アイデアを付箋のように書き溜める」工程）の妨げになる。
* **Decision:**
  ソケットを持たない軽量な **「メモ付箋（`note`）」** をダブルクリック1つで即座に配置できるようにし、後からワンクリックで **「シーン（`scene`）」「キャラクター（`character`）」「伏線（`foreshadow`）」「設定・アイテム（`world_item`）」** へ変換（昇格）できる設計とする。

## ADR-004: `genkou_sheet` との連携設計（構成案出力・原稿ファイル紐付け）
* **Status:** Accepted (2026-11-15)
* **Context:**
  本ツールは `genkou_sheet`（原稿執筆）の前工程および伴走ツールとして機能するため、プロットから執筆へスムーズに移行できる仕組みが必要。
* **Decision:**
  1. 各シーンノードに原稿ファイルパス（`manuscriptPath`: 例 `01_opening.txt`）を紐付け可能とし、ノードから直接原稿ファイルを作成・オープンできるようにする。
  2. 時系列フロー（`Flow` ソケット）のトポロジカルソート順に基づき、章立て・あらすじ・伏線チェックリストをまとめた構成案（Markdown / テキスト）の出力、および `.genkou.json` の原稿順序リストへの同期機能を提供する。

## ADR-005: 他プロジェクトへの非干渉と対象フォルダー限定動作
* **Status:** Accepted (2026-11-15)
* **Context:**
  `genkou_sheet` と同様、通常のプログラミング用ワークスペースに一切干渉しない仕組みが必要。
* **Decision:**
  `activationEvents` は `workspaceContains:.nplot.json` / `workspaceContains:.genkou.json` および `.nplot` ファイル開封時のみとし、コマンド `Node Plot: このフォルダーをプロットプロジェクトとして有効化` を実行したワークスペースでのみ専用設定ファイルを構成する。

## ADR-006: パン・ズームはファイル編集として扱わない
* **Status:** Accepted (2026-11-15)
* **Context:** パン・ズームのたびに `UPDATE_DOCUMENT` を送っていたため、眺めるだけでファイルが「変更あり」になり、Undo（⌘Z）の最初の数回が視点移動の取り消しに消費されていた。
* **Decision:** パン・ズーム・ワイヤー表示・パネル開閉は Webview の `setState` に保存し、単独ではドキュメントを更新しない。`viewport` フィールドはスキーマに残し、他の編集を確定する際に現在値が一緒に書き込まれる。`DOCUMENT_CHANGED`（Undo・外部変更）受信時は現在の視点を維持する。
* **Consequences:** 閲覧だけではファイルが汚れない。新しいパネルで開いた場合はファイル内の最後の `viewport` から表示される。

## ADR-007: 枠の入れ子・所属はジオメトリから導出し保存しない
* **Status:** Accepted (2026-11-15)
* **Context:** 「キャラクターを組織で束ねる」ための入れ子枠が必要。`parentFrameId` / `frameId` を保存する方式は、手作業の JSON 編集や枠のリサイズで実際の配置と保存値が食い違う恐れがある。
* **Decision:** 所属は常に座標から導出する（ノードはアンカー点を含む最小の枠、枠は自分を完全に含むより大きい最小の枠が親）。純粋関数として `src/core/frameLayout.ts` に実装する。
* **Consequences:** スキーマ変更は `PlotFrame.colorTag` の値域と `PlotNode.width` / `certainty` の追加のみ（後方互換）。見た目と所属が常に一致する。代償として、枠を重ねて配置すると意図せず入れ子になる（インスペクタの所属パス表示で確認できる）。

## ADR-008: セリフはノードではなく `PlotDocument.lines` に保持する（2026-11-15）
* **状況:** プロット確定後に各キャラのセリフを書き溜め、どこにハマるか未定のまま後から配置する執筆スタイルに対応したい。
* **決定:** セリフはキャンバスのノードにせず、独立した配列 `lines` に保持し、話者・シーンは ID 参照する。状態（未配置／候補／確定）は保存せず参照から導出する。参照先の無い ID はパースで捨てず、ノード削除操作（`removeNodes`）のときだけ掃除する。
* **理由:** セリフは数百件規模になり、ノード化するとキャンバスが埋もれる。状態を保存しないことで「確定なのに確定先が無い」不整合が起きない。ID を保持するのは JSON 編集・Undo の途中状態でセリフの紐付けを失わないため。
* **影響:** `lines` は省略可能（未使用ファイルの差分を出さない）。ビュー種別に `lines` を追加。
